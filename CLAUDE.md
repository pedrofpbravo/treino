# CLAUDE.md - "Treino" (Gym tracking PWA)

Architecture notes for future sessions. This describes the app as it actually is (v7.6).

# Orchestration Protocol: Opus plans and orchestrates, Sonnet implements, fresh Sonnet reviews

The main session runs on **Claude Opus 5.5** and is the **orchestrator and tech lead**. It is not the implementer. Its job is to plan, delegate, define the tests, and own final quality. All code is written by **Sonnet subagents**, and all review and testing is done by **separate, fresh Sonnet subagents** that did not write the code. Codex is not used.

## Hard rule: the orchestrator does not touch the code

- **The orchestrator never creates, edits, or deletes files under the project** (`js/`, `index.html`, `sw.js`, `firestore.rules`, `*.json`, anything the app ships). Not "just one line", not a typo, a version bump, a CSS value, or a one-character fix. Every change to a shipped file goes to an implementer agent as a brief.
- **The orchestrator does not write the tests or verification scripts either.** It specifies what must be proven; the reviewer agent writes and runs the check and reports the output.
- **The orchestrator may only:** read files, search, run read-only commands (`git status`, `git log`, `git diff`, reading logs), write `WORKLOG.md` and this `CLAUDE.md`, and run git commit/push when the user asks.
- The only exception is an explicit instruction from the user in chat, in that turn, such as "do this one yourself". Standing permission does not exist; it expires at the end of that task.

## Roles and models

Spawn agents with the Agent tool and set the model explicitly every time.

| Role | Who | Model | Does |
|---|---|---|---|
| Orchestrator | the main session | Opus 5.5 (the user selects it for the session) | plans, writes briefs, defines acceptance criteria and tests, decides, closes out |
| Implementer | subagent, `model: "sonnet"` | Sonnet | writes and edits all code, fixes what review finds |
| Reviewer / tester | NEW subagent, `model: "sonnet"` | Sonnet | reads the diff, runs the app and checks, reports evidence; edits nothing |

- **Reviewers are always fresh.** Never reuse the implementer for review, and never reuse an earlier reviewer for a later round. A new agent has no stake in the implementation and no memory of its shortcuts.
- **Reviewers are read-only.** They report findings with evidence. Fixes go back to an implementer.
- Never override the model to anything other than Sonnet for implementers and reviewers, and never use a Codex path.

## Workflow (follow in order)

1. **Plan first.** When the user gives a task, produce a short plan: objective, deliverable(s), task breakdown, which brief covers what, and the acceptance criteria. Ask ALL scope questions in one batch (one message or one AskUserQuestion), then wait for approval before delegating. The plan says what the implementers will do, never "what the orchestrator keeps", because the orchestrator keeps no implementation.
2. **Delegate implementation.** One Sonnet implementer per clearly scoped task. Each brief must be **self-contained** (the agent has none of our conversation context). Include: exact deliverable and file paths, inputs and assumptions, structure required, acceptance criteria, which files may change (and that nothing else may), and what NOT to do (no commit, no push, no new dependencies, no build step). Point it at this file for the architecture rules.
3. **Serialize briefs that touch the same file.** Two implementers editing `js/main.js` at once clobber each other. Dispatch the second only after the first lands. Independent files can run in parallel.
4. **Delegate review and tests to a fresh Sonnet.** After the implementer reports done, spawn a NEW Sonnet reviewer with: the acceptance criteria, the list of changed files, and the checks to run (diff read, `#debug` run, console and network logs, screenshots where relevant, greps for forbidden patterns). It must report raw output and a pass/fail per criterion. "It works" without evidence is not accepted.
5. **Orchestrator review, never trust.** Read the diff and the reviewer's evidence yourself and compare against the acceptance criteria. This is reading and running only, never editing.
6. **Send every fix back to an implementer.** Anything found in review, big or small, cosmetic or structural, goes to a Sonnet implementer as a follow-up brief (resume the same implementer when useful). Improvements the orchestrator thinks of go the same way. Then a NEW reviewer checks again. Repeat steps 2 to 6 until the acceptance criteria pass.
7. **Close out.** Summarize: what was built, which briefs the implementers received, what the reviewers found and how it was fixed, and remaining risks or open items.

## Rules

- Never present agent output as done without your own review pass.
- One delegation = one clearly scoped task. No vague multi-part briefs.
- If an agent fails repeatedly or is blocked, stop and tell the user. Do not silently do the work yourself. A blocked agent is a status report, not a license to implement.
- Keep a running `WORKLOG.md` in the repo: plan, delegations sent, results received, review findings, follow-up briefs.
- Code: runs cleanly from a fresh shell; minimal dependencies; brief README or header comment.
- **Token economy: batch everything.** Ask all scope questions up front, one brief per phase with its acceptance checks bundled into a single consolidated reviewer run, one status report per phase. Have agents return findings and key output, not full file dumps.
- **Deploy ritual:** every deploy bumps `CACHE` (sw.js) and `APP_VERSION` (main.js), done by an implementer. Committing and pushing (which publishes via GitHub Pages) happen only when the user asks.

## What it is

Personal gym-tracking app for one person (Pedro), UI in pt-BR, installed as a PWA on an iPhone from GitHub Pages (`pedrofpbravo/treino`). Owner is not a developer; keep changes simple and explain deploys.

Until v4 the app also carried a bathroom/Bristol log; that feature moved to its own app, Intest (`05. app intest`), in Sep 2026, together with its Firestore history.

## Functionality (4 tabs)

- **Treino**: pick a program (dropdown + Gerenciar sheet) and a day (chips). Day chips show a "✓" for days trained in the current program cycle, and that comes ONLY from an explicit finished session (`cycleProgress()`, see Key behaviors). Each exercise is a compact uniform-height card: name + target pill ("3×12"), a "Ref: <kg>" line that also carries the state badge on its right (`✓ feito`, or `2/3 séries` while in progress), one-line note. There is NO checkbox on the card (removed in v7: tapping it to expand kept deleting the log). Since v7.1 a workout in progress is a LOCAL DRAFT (`gym:drafts` in localStorage, keyed `"date|dayId"` per exercise), never a Firestore write: tapping the card body starts the exercise by creating its draft, pre-filled purely from the day target (`prefillSets(entry, refWeight)`: targetSets rows of the target reps at the exercise's reference weight; the last session never feeds the prefill — if today's log already exists, e.g. finished + reopened, the draft seeds from it via `draftFromLog`). The inline sets editor (kg-first per set, per-set check toggle, add/remove set) mutates the draft and re-saves it to localStorage only. Tapping a started card collapses/expands it. Checking a set auto-starts the 90s rest timer; checking the LAST pending set auto-collapses the card and marks it done. Card state comes from the draft: peach fill + `✓ feito` only when ALL sets are checked (`draftAllDone`), accent left edge only with ≥1 checked set, and a merely opened card (0 checked) looks idle with a `0/N séries` badge — expanding/collapsing never changes color and never records anything. Drafts from previous dates are pruned on render: an unfinished workout is discarded, by design. **Nothing on the Treino tab deletes a log**: removal happens only in Histórico (swipe). v7.4: o editor de sets trava em 8 séries (`MAX_SETS`, logic.js) e todos os editores de alvo clampam com `clampTargetSets`; "Editar dia" na aba Treino virou "editar exercícios de HOJE" (add/remove/reordenar gravado como override `__entries` no draft local, expira com ele; a edição permanente completa vive em Ajustes > Treinos via `openDaySheet(id, {scope:"permanent"})`); o ⚙ segue permanente para séries/reps e sincroniza o override quando ele existe. Um card não iniciado pode mostrar a linha `.wc-suggest` (swap-back): se o exercício previsto já foi feito neste ciclo como substituto de outro ainda não feito, um botão "Trocar" aplica a substituição de hoje (`swapBackSuggestion` em logic.js, dados do campo `substitutedForId` dos logs). "Finalizar treino" is the ONLY moment logs are written: one log per exercise with ≥1 checked set, containing the checked sets only (0-checked exercises stay out of the history), then the finished session — all fire-and-forget so it works offline; v7.4: antes de gravar, `reviewAndFinishWorkout()` valida pesos (série destoando >25% E >5kg da referência = último peso logado, fallback refWeight) e abre a sheet empilhada `#sheet-finish-check` para confirmar ou voltar; ao gravar, se o maior peso marcado superar o refWeight do exercício, o refWeight sobe para ele (nunca desce); the draft is kept for the rest of the day, so cards stay painted and re-finishing after a reopen overwrites the same deterministic log ids. It records the session even when exercises remain incomplete; while a workout is open, a sticky "Treino em andamento · Finalizar" bar appears once that button scrolls out of view (IntersectionObserver). Long-press (~350ms) a card to drag-reorder the day's exercises (persists entry order via updateDay). The ⚙ gear opens the quick-detail sheet (day target + refWeight/note + a "Histórico" link row that opens the full exercise log). "＋ Cardio" (always visible, standalone) opens a sheet: type dropdown, whole minutes, note; today's cardio entries list below with a remove ×. Rest timer presets (60/90/120s) live inline AND inside the floating bar; the bar (Treino tab only) counts down and at zero just blinks at 0:00 until dismissed (X, a new preset, or checking exercise/set). No sound, no vibration (both removed in v7). A running timer survives reloads; a finished one doesn't.
- **Exercícios**: the full catalog grouped by primary muscle, accent-insensitive search, muscle-chip filters (toggling a filter resets the page scroll to top — v7.1, otherwise the shrunken list left the viewport clamped mid-air and read as a broken layout). Tapping opens the full edit sheet (name, primary/secondary/other muscles, refWeight, note, delete, plus a "Histórico" link row on existing exercises).
- **Séries** (aba, v7.2/v7.4): séries semanais por músculo (1 primário / 0.5 secundário) com toggle Semana/Dia (`state.seriesView` + offsets independentes, futuro bloqueado); linhas do breakdown são clicáveis (abrem a sheet de cadastro; exercício deletado abre o exlog).
- **Histórico**: three views. "Sessões" = trained-days-per-week bar chart (union of workout and cardio dates; v7.4: 8 semanas, labels "dd-dd/mm" no primeiro/meio/último via `showLabels:"ends-mid"` do barChart) + sessions grouped by date/day with swipe-to-delete rows (sets string in small grey wrapping text); v7.4: o nome do exercício é clicável (sheet de cadastro, com `suppressClick` pós-swipe). "Cardio" = minutes-per-week bar chart + weeks (newest first) with per-day minutes and types. "Progresso" = per-exercise max-weight line chart + last-10 table.
- **Ajustes**: muscle-group manager and cardio-type manager (rename, reorder, delete-if-unused), seção "Treinos" (v7.4: lista programas/dias, abre o editor PERMANENTE de dia; v7.6: estrela ★/☆ por programa marca o FAVORITO), JSON backup export/import, logout, version label.

## Architecture (same family as MercadoJá / Intest)

- **Vanilla JS, no build step.** ES modules loaded directly by the browser; Firebase SDK 10.12.2 as ESM **vendored into `js/vendor/`** (same origin since v7, no gstatic on cold start). Do NOT introduce Vite/React/npm. To upgrade the SDK: re-download the three files from `https://www.gstatic.com/firebasejs/<version>/`, re-apply the local import-specifier rewrite (they import each other as `./firebase-app.js`), and bump `CACHE` in sw.js.
- **Firebase**: Auth (one personal email/password account, `browserLocalPersistence`, sign-up disabled in the console) + Firestore with `persistentLocalCache({tabManager: persistentMultipleTabManager()})` for full offline. Keys are hardcoded in `js/config.js` (public by design); security lives in `firestore.rules`, which pins everything to Pedro's hardcoded UID (`request.auth.uid == "GjkT..."`).
- **Reads**: one `onSnapshot` per root collection, whole collection pulled, sorted/filtered client-side in `logic.js`. **Writes**: small targeted `setDoc`/`updateDoc`/`writeBatch` with `serverTimestamp()`, optimistic UI (the local cache fires the snapshot immediately, so the UI re-renders from one source of truth and feels instant offline).
- **`#debug`**: `main.js` swaps `db.js` for `fakedb.js` (`const db = location.hash === "#debug" ? fakeDb : realDb`). fakedb mirrors every export and ships the real seed catalog plus ~6 weeks of generated logs, so every screen works with zero Firebase.
- **Seeding**: triggered from a snapshot handler when a collection comes back empty, guarded by `state.seededX` flags, fixed doc ids so concurrent seeding is idempotent. Seed data lives in `js/seed.js` (pure data).
- **SW** (`sw.js`, rewritten in v7): `PRECACHE` lists the whole shell (html, css, every `js/` file including `js/vendor/*`, icons) and `install` fetches it all with `cache: "reload"`; `fetch` is cache-first with background revalidation, and navigations are served from the cached `index.html`. This is what killed the multi-second white screen on resume; the old network-first strategy waited on the network before touching the cache. Caveat: `install` uses `addAll`, so ONE 404 in `PRECACHE` fails the whole install. Keep the list in sync when adding files. DEPLOY RITUAL: bump `CACHE` (sw.js) and `APP_VERSION` (main.js) on every deploy; force-close and reopen the PWA on the phone (the first reopen installs the new worker, later launches boot from cache).
- Hosting: GitHub Pages from repo root, or `firebase deploy` (firebase.json ships hosting + rules).

## Files

- `js/config.js`: firebaseConfig only ("the only file you edit").
- `js/seed.js`: pure data. 14 muscle groups, 27 exercises (owner's real catalog with refWeight + machine-adjustment notes), 2 programs with per-day entries.
- `js/logic.js`: pure helpers (no DOM/Firebase): normalize, local date handling, logDocId, lastLogFor, prefillSets, entryReps, parseRefWeight, setsLabel, groupSessions, progressionSeries, exerciseHistory, weeklyFrequency, sorting.
- `js/charts.js`: pure SVG-string builders (lineChart, barChart). No chart libraries.
- `js/db.js`: the only file touching Firebase. Flat verb-named API.
- `js/fakedb.js`: same exports, in-memory.
- `js/main.js`: all UI. State object + renderers + wiring + boot.

## Data model (Firestore root collections)

- `muscles/mus-<key>`: `{name, order}`
- `exercises/ex-<slug>` (seeded) or random id: `{name, nameLower, primaryMuscleId, secondaryMuscleIds[], otherMuscleIds[], refWeight, note, createdAt, updatedAt}`
- `programs/prog-<slug>`: `{name, nameLower, order, createdAt}`
- `days/day-<prog>-<slug>`: `{programId, name, order, entries: [{exerciseId, targetSets, reps}]}` (flat collection, NOT a subcollection; entry order = card order; targets are per day because the same exercise has different targets on different days). Single rep number per entry ("3×12"). Docs written before v2 carried `repMin`/`repMax`; `entryReps()` in logic.js reads those as the range top, no migration.
- `logs/log-<date>-<dayId>-<exerciseId>`: `{date "YYYY-MM-DD" LOCAL, programId, dayId, exerciseId, substitutedForId (v7.4: id do exercício ORIGINAL quando o log veio de um substituto, senão null; logs antigos não têm o campo e importam como null), exerciseName, dayName, programName, sets: [{reps, weight|null, done}], ts}`. Since v7.1, written ONLY by "Finalizar treino" and carrying the checked sets only (all `done: true`); the deterministic id makes re-finishing an overwrite, not a duplicate. Name snapshots keep history working after deletions. Logs written before v6 have no `done` per set; `cloneSets()`/`draftFromLog()` treat a missing flag as done (no migration).
- `sessions/sess-<date>-<dayId>`: `{date "YYYY-MM-DD" LOCAL, programId, dayId, dayName, programName, finishedAt}`. Presence means the workout was explicitly finished; deterministic ids make finish idempotent, and deleting the doc reopens it. Name snapshots keep history readable after renames or deletions.
- `cardioTypes/ct-<key>`: `{name, order, note}` (seeded: bike "Bike s/ suporte", bike-suporte "Bike c/ suporte", eliptico, esteira, escada, corrida, remo, outro; managed in Ajustes like muscles, name + note editable per row). The note is a machine-adjustment description shown as a muted hint in the "+ Cardio" sheet when that type is selected.
- `cardio/<random id>`: `{date "YYYY-MM-DD" LOCAL, typeId, typeName (snapshot), minutes (int), note, ts}`. Standalone (no program/day); multiple entries per day allowed; delete-only editing (remove + re-add).
- (Removed in v5: the `bathroom` collection. Data migrated to the Intest app's Firebase project; the old collection is deleted from this project once migration is confirmed.)

## Key behaviors and decisions

- Dates are always LOCAL strings built from getFullYear/Month/Date. Never `toISOString()` for dates (UTC shifts the date in Brazil after 21:00). A workout crossing midnight logs the remaining exercises on the new date (accepted).
- Starting an exercise pre-fills purely from the day entry's target: targetSets rows of `reps`, weight = `parseRefWeight(refWeight)`. The last session NEVER changes the prefill (v7.1; it lives only in the history) — adjustments happen by editing inside the card or the ⚙ sheet. Nothing is saved to Firestore until "Finalizar treino"; completion is per-set inside the local draft.
- Reference weight everywhere is derived from logs (fallback: exercise `refWeight` string). Never stored on the exercise. refWeight is numeric-only since v6 ("kg" is rendered outside the input); a one-time client migration (localStorage flag `gym:migrate-refweight-v6`) extracted the number from old free-text values and moved leftovers into the note. **Decimals use the DOT everywhere** (v7): `82.5`, and `85` stays `85`. Weight fields are `type="text" inputmode="decimal"` (not `type="number"`, which silently discarded the comma the iOS pt-BR keypad produces) and normalize on input via `normalizeDecimalInput()` / `parseDecimal()` in logic.js. Legacy free-text refWeights ("40–42,5 kg") still render untouched.
- One-time boot upserts guarded by localStorage flags: refWeight migration (`gym:migrate-refweight-v6`), the `ex-agachamento-smith` catalog add (`gym:seed-smith-v6`), and the bike split + 02-03/09 cardio backfill (`gym:cardio-bikes-v6-1`, fixed doc ids `backfill-2026-09-02-bike` / `backfill-2026-09-03-eliptico`). v6.5 adds the finished-session backfill (`gym:session-backfill-v6-5`, `FINISH_BACKFILL_DATES`): for each listed date it marks every day logged that date as finished, resolving programId/dayId from the logs at runtime so no hardcoded id can go stale. It retries on the next snapshot if the logs have not arrived yet. v7.4 adds `gym:prog3x-v7-4`: substitui as entries dos 3 dias de `prog-fb-ul` pela tabela nova do Pedro (matching por nameLower em runtime via `resolveProg3xEntries` em logic.js, cria 5 exercícios que faltavam, um writeBatch `db.applyProgram3x`); a flag NÃO é persistida em `#debug` para não queimar o domínio antes do deploy. v7.6 adds `gym:prog4x-v7-6`: cria o programa `prog-ul4x` "Upper Lower 4x" (dias `day-ul4x-upper-a|lower-a|upper-b|lower-b`) já como favorito, com 5 exercícios novos; resolução por slot em `resolveProg4x` (logic.js) = id fixo primeiro, depois nameLower, depois create; "T bar row" só casa por nome (sem create, ausente = aborta com toast); pula se `prog-ul4x` já existe (protege edições se a flag sumir); um writeBatch `db.createProgram4x`. Em `#debug` o fakedb ganha o exercício extra `dbg-t_bar_row`.
- Programa favorito (v7.6): campo `favorite` (boolean) no doc do programa, no máximo um true (`db.setFavoriteProgram(id|null, allIds)`, um batch). `sortProgramsFavoriteFirst` (logic.js) põe o favorito no topo de TODAS as listas (só exibição, `order` intacto). No boot, uma vez por carregamento (`applyFavoriteOnBoot`), a aba Treino abre no favorito com o último dia usado nele (`gym:dayByProgram`), sem exceção para draft em andamento (decisão do Pedro). `setSelectedDay()` é o único lugar que atribui `state.dayId`. Backup exporta/importa `favorite`.
- Day-cycle checks come ONLY from explicit `sessions` records dated on or after `CYCLE_START` (`js/logic.js`, `"2026-09-08"`); logs never mark a day. `cycleProgress(programId, days, finished, cycleStart)` replays the finished sessions chronologically and returns `{trained, total, completed}`; when a cycle fills, `trained` empties and `completed` describes it (key, date, ordered days). Finishing the fifth day therefore opens the `#sheet-cycle` "Semana concluída" modal (once per cycle, guarded by `localStorage["gym:cycle-celebrated:<programId>"]`, fired from the `onSessions` snapshot) and the chips come back clean. Logging or completing exercises on the last day changes nothing until "Finalizar treino" is pressed. `CYCLE_START` is a read-time filter only: Histórico still shows everything.
- Backup: export builds `{app, version, exportedAt, muscles, exercises, programs, days, logs, sessions, cardio, cardioTypes}` and goes out via the iOS share sheet (fallback: blob download). Import preserves doc ids (non-destructive merge, overwrite-by-id), chunked 400 writes/batch. Old backups without `sessions`/`cardio`/`cardioTypes` import fine; a v4 `bathroom` array is silently ignored.
- Deleting an exercise removes it from all days in one batch and keeps logs (soft-orphan). Deleting a muscle is blocked while referenced. Deleting a program cascades its days, keeps logs.
- Exercise log sheet (v6.4): `sheet-exlog` lists every session ever logged for one exercise, newest first, one line per set ("Série 1 · 11×35kg"); unchecked sets render dimmed with a "pendente" tag. It is a STACKED sheet (`.sheet-stack`, z-index 55 over the normal 50): it opens on top of the sheet that launched it and its "Fechar" button hides only itself, so a half-typed exercise form survives the round trip. It re-renders live from `onLogs` while open. All sessions are rendered (no paging); the data is already in memory.
- Rest timer stores the absolute end time in `localStorage["gym:timerEnd"]`; a running countdown survives reloads. Checking a set calls `startTimer(DEFAULT_REST_SECS)` (90s); the 60/90/120 buttons in the bar restart it at that duration for that one rest, and the default stays 90. At zero the bar just blinks at 0:00 until dismissed (X, new preset, or exercise/set check via `clearFinishedTimer()`); the finished state is in-memory only. No audio and no vibration since v7 (the WebAudio bell and `navigator.vibrate` were removed).
- localStorage keys: `gym:program`, `gym:day`, `gym:dayByProgram` (v7.6: `{programId: dayId}`, último dia por programa), `gym:timerEnd`, `gym:collapsed` (collapsed workout cards, keyed `dayId|exerciseId`), `gym:workoutStart` (`<date>|<dayId>` of a workout started by tapping the button), `gym:drafts` (v7.1: the in-progress workout, `{"date|dayId": {exerciseId: sets[], __subs: {originalId: substituto}, __entries: [entries override de hoje]}}` — chaves com prefixo `__` são metadados reservados e nunca marcam o dia como iniciado (`draftHasExerciseSets`); pruned to today on every Treino render — the ONE localStorage key holding real workout data until "Finalizar treino" flushes it to Firestore), `gym:cycle-celebrated:<programId>` (last celebrated cycle key), plus one-time flags `gym:migrate-refweight-v6`, `gym:seed-smith-v6` (UI prefs/flags only otherwise; all recorded data lives in Firestore).
- Theme (v2): cream `#f8f3ec` bg, ink `#1e1e1c`, peach accent `#f0916a`, pill buttons. Viewport is locked (`maximum-scale=1` + `touch-action: manipulation`) so double-tap never zooms.
- Swipe-to-delete (v4): `makeSwipeable()` in main.js wraps history rows; swipe left reveals "Remover", right-click on desktop.
- UI text is pt-BR.

## Local dev

`python -m http.server 8095` (also in `.claude/launch.json`), then http://localhost:8095/#debug. Two gotchas: `autoPort` in launch.json announces a fresh port but still launches the server on 8095, so if 8095 is taken the process dies instantly and the announced URL answers nothing; and stale `python` servers from earlier sessions pile up on 8087/8093/8095 (four of them on one port produced `ERR_EMPTY_RESPONSE`). Check with `netstat -ano | grep :8095`, kill the strays, then start the preview. Debug hooks: `window.__state`, `window.__buildBackup`. Note: the SW caches aggressively even on localhost; when testing fresh edits, unregister the SW + delete caches or hard-reload, or stale JS will produce ghost bugs.
